# 04 加密协议验证原型

本阶段仅产出可运行协议原型、固定测试向量和最终 wire-contract 文档，不处理真实页面。先回答一个问题：知道所有 Hub 状态并可篡改/重放中继流量的服务端，能否读取内容或让端点执行伪造请求？通过后才实施 05。

确定约束：重新生成 256-bit 主秘密，由扩展本地生成并经带外配对交给 CLI。主秘密永不发送 Hub。使用 Web Crypto 标准原语，HKDF-SHA256 用独立标签派生 Hub 鉴权材料及端点密钥；Hub 所见材料不得反推内容密钥。新的 driver 格式显式带版本，关联选定 origin；旧 br-secret 明确拒绝并提示重新配对，不能自动升级已泄露给 Hub 的秘密。

原型先验证 PSK 认证会话与 AES-GCM 信封，区分双向密钥；每次扩展重启/重新连接建立新会话，认证绑定协议版本、双方随机挑战、route 与 origin。信封认证覆盖 session、direction、requestId 与序号；每次密钥下 nonce 唯一，重放窗口有界，窗口外拒绝，过期会话拒绝。不得仅依靠短期 task 缓存防重放。多 CLI 并发须有独立会话与资源上限。此方案不承诺前向保密；如必须具备，在原型阶段改用经过审阅的现成握手方案。

下一步必须在 wire-contract 写定：字节编码、派生标签、握手 transcript、nonce/序号生成、并发及乱序接受规则、会话失效、额度、测试向量、失败码。这里有意安排为研究切片；05 不得由实现者临时发明这些规则。

验证：Node↔浏览器向量互通；恶意 Hub 改 payload/header、反射方向、替换会话、重放、重启后注入旧包全部拒绝且不触达执行器；仅掌握 Hub token 无法解密或完成端点认证。原型需独立协议审阅，审阅结论写入本片。可委派内部文件名和测试编排；密码协议冻结前不进入真实 RPC。
